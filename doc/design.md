# 设计文档

## 1. 设计目标与总体方案

elevate-kit 采用“单一宿主程序、按需启动、单请求特权进程”的运行时模型。应用提供一个宿主程序，其中包含任务注册和任务执行所需的逻辑；普通进程在需要执行特权任务时，请求启动该宿主对应的特权进程。每个特权进程最多处理一个请求，在发送响应或明确报告失败后退出；如果加载、任务执行或阻塞输入输出没有返回，进程可能继续存在。

这里的“普通进程”指发起请求的一侧，“特权进程”指由平台特权机制启动、负责执行任务的一侧。特权进程不是常驻服务，也不是独立的安全中介。宿主程序及其可加载模块共同构成实际的任务执行边界。

该方案避免为每个任务维护一个长期运行的特权服务，同时让平台原生的提权和授权机制参与进程启动。代价是重复启动和授权可能产生延迟，且单请求进程不能提供跨请求状态或统一的全局调度。

## 2. 参与者与生命周期

运行时包含以下参与者：

| 参与者 | 职责 |
| --- | --- |
| 普通进程 | 设置应用身份，发起任务请求，等待结果并处理失败。 |
| 宿主程序 | 作为普通进程或特权进程运行，包含任务注册、请求处理及平台适配逻辑。 |
| 特权进程 | 由宿主程序在特权上下文中启动，载入请求指定的模块，执行一个任务并返回结果。 |
| 操作系统特权设施 | Windows 上的 Task Scheduler/UAC，Linux 上的 pkexec/Polkit；负责特权进程的启动或授权。 |
| 本地 IPC 对端 | 在一次调用中连接普通进程和特权进程，传输请求及响应。 |

普通进程首先确定应用 ID，并准备任务请求。调用机制根据应用 ID、宿主位置和平台状态准备特权启动条件；首次使用时可能需要平台授权或修复。特权进程启动后建立本次调用专用的 IPC 会话，执行对端 PID 和可执行文件路径检查，解析请求并尝试动态加载请求中的模块，查找并执行已注册任务，发送结果，然后关闭会话并退出。请求解析和路径一致性检查不构成任务授权或完整的请求认证。

特权进程的生命周期与单个请求绑定。普通进程不会依赖特权进程保留任务状态；任务需要的全部输入必须通过请求参数传递，结果必须通过响应返回。生命周期上限只适用于正常完成或显式失败的处理，不会强制终止卡住的加载、任务或输入输出。

宿主的内部启动参数缺失或非法时，Process 只返回，不产生消费结果，也不会把该启动转换成任务请求。因此，经 pkexec 启动但没有合法内部参数的进程，其后续行为不能由内部参数解析兜底；宿主必须在普通逻辑中自行约束这类启动场景。

## 3. 平台启动与授权

### Windows

Windows 使用 Task Scheduler 作为按应用 ID 区分的特权启动基础，首次建立或修复配置时可能经过 UAC。任务由当前管理员的交互令牌以最高权限启动，不是以 SYSTEM 身份运行的服务。Task Scheduler 负责按安装位置和应用配置启动宿主程序；启动后，普通进程与特权进程通过 Windows Named Pipe 建立本次会话。

Windows Release 部署要求特权宿主位于 Program Files 目录下。启动前会检查宿主位置是否符合该约束，以避免从不受保护的开发或临时目录建立生产特权入口。该路径约束不替代对安装目录、依赖和模块的访问控制。

### Linux

Linux 使用 pkexec 请求特权启动，并由 Polkit 提供授权配置。应用对应的 Polkit 文件使用固定的系统目录。policy 将授权绑定到宿主可执行文件路径；rule 对匹配的派生 action 无条件返回 YES，不限制用户、会话或参数。因此，经 pkexec 发起的非内部启动风险不能由该 rule 消除，宿主必须在普通逻辑中自行约束可接受的启动场景。

启动前会检查 host 文件存在。Release 部署还要求 host 由 root 拥有且不可被所有用户写入（非 world-writable）。生成的 policy 预期绑定当前宿主路径；内容不匹配时只记录日志，最终 readiness 仍取决于 host 检查和 pkcheck。配置修复返回失败也不会阻止本次已经提权的任务继续。这些检查用于降低普通用户替换特权入口的风险，但不能覆盖所有文件系统、挂载、依赖库或管理员配置问题。

## 4. 任务模型与模块

任务通过静态注册进入宿主程序的任务表，也可以通过公开接口在运行时注册；同名注册会覆盖原有任务。任务名称由注册项确定，任务接收一个 JSON 参数值并返回一个 JSON 结果值。JSON 是任务边界上的数据表示，任务实现自行决定参数对象的字段、类型和校验规则；库不为业务参数提供通用模式校验。

模块路径（modulePath）可以由普通调用方随请求提供。特权进程在分派任务前尝试按该路径动态加载模块，并在模块完成注册后查找请求的任务。因此，任务可以位于宿主程序本体或请求所指向的可加载模块中，具体可用任务取决于实际载入结果。

模块路径是安全敏感输入。当前实现不检查其所有者、权限、位置、签名、来源、完整性或 allowlist，也不提供其他信任校验。宿主程序、模块路径及该路径上的可加载模块都必须由部署方预先置于受信任且受保护的位置；普通进程或请求构造被操纵的情况不在防御范围内。动态加载本身不构成安全保证，也不能视为无风险机制。

## 5. IPC 会话与一致性检查

每次调用使用独立 IPC 会话，不依赖跨请求连接或共享会话状态。Windows 传输使用 Named Pipe，Linux 传输使用 Unix socket。普通进程发送任务名称、JSON 参数及模块路径，特权进程返回任务 JSON 结果或失败状态。消息使用长度前缀，当前没有业务层面的大小上限；后续读写也没有统一超时。

连接建立后，特权进程检查对端可执行文件路径与预期路径相同。普通进程接受启动 PID 相同或对端可执行文件路径相同的连接。Linux 从 SO_PEERCRED 取得对端 PID，但不检查对端 UID。Linux 的 Unix socket 位于 /tmp 时，会在绑定前删除同路径项；实现不显式检查旧项所有者，也不设置专用 socket 权限。

这些检查是本地进程间协议的约束，不是完整的调用方认证体系。实现不声称提供安全 broker，也不保证能识别所有能够影响进程、文件、IPC 命名空间或系统授权配置的本地攻击者。

## 6. 应用 ID

应用 ID 用于区分平台启动和授权配置，使不同产品或不同宿主不会意外共享同一套特权配置。它不应承担用户身份、调用方身份或模块来源证明的职责。

调用方负责提供稳定、唯一且适合部署的 ID。当前实现不验证、不转义显式设置的 ID，也不负责处理命名冲突；未显式设置时，默认使用当前进程的文件名。应用 ID 会参与 IPC 名称、任务名称以及 Polkit 文件名和文件内容的生成，因此必须是受信任配置，不能直接使用不可信输入。调用方仍须避免碰撞、避免依赖不稳定的路径片段，并遵守平台命名和部署约束。应用 ID 本身不是秘密，也不是授权凭据。

## 7. 结果、等待与失败边界

任务成功时，调用端只接受 JSON 对象。任务返回 null、数组、标量或布尔值时，调用结果会折叠为 null；无法连接、启动失败、协议失败、任务执行失败或等待超时等情况也可能表现为 null JSON。实现没有结构化失败响应，调用方必须将 null 视为没有得到成功结果。

任务结果的正常设计边界是 JSON 对象；库不将失败自动转换为业务异常，也不替调用方定义任务级错误结构。

约三秒预算只覆盖特权进程已启动后的 Accept 阶段，且只到请求发送前。超时时，可能继续的是已经启动的特权进程、授权提示或配置处理；该请求尚未被提交为任务。请求发送后没有统一时限，调用方不能据此证明任务未执行，也不能通过取消操作可靠地终止任务。

当前没有取消协议。调用方不能通过取消操作可靠地终止已发送的任务；需要可重复、可恢复或避免副作用的任务时，任务自身和调用方必须设计幂等性、状态查询或外部补偿机制。

## 8. 设计决策原因

- **单一宿主程序**：让平台授权、任务注册和模块加载围绕一个明确的可执行入口组织，减少常驻特权服务的部署面和状态管理成本。
- **按需、单请求特权进程**：避免长期持有特权上下文，缩短特权进程生命周期；代价是启动开销、授权延迟和没有跨请求状态。
- **静态任务注册**：使任务集合在模块载入后由程序自身确定，避免引入动态任务发现协议；代价是任务必须随宿主或模块构建并正确注册。
- **JSON 参数和结果**：提供跨进程、语言库易处理的数据边界，减少 ABI 对业务类型的耦合；代价是类型约束和业务错误需要由任务自行定义。
- **独立本地 IPC 会话**：将一次调用的连接状态限定在一个请求内，便于进程退出和故障隔离；代价是不能复用连接，也没有取消或批量请求能力。
- **PID 与可执行路径检查**：在本地 IPC 层增加对预期宿主的绑定，降低误连风险；这不是完整认证，也不能替代受保护安装和受信任模块。
- **平台原生提权**：Windows 采用 Task Scheduler/UAC，Linux 采用 pkexec/Polkit，以复用操作系统的授权和启动边界；代价是平台配置、权限策略和用户提示行为各不相同。

## 9. 信任假设

本设计假设部署方能够保护宿主程序、普通进程的请求构造逻辑、依赖库、可加载模块、固定的 Polkit 配置目录以及相关安装目录。宿主和模块被视为受信任代码，模块路径被视为部署方负责的安全敏感配置。也假设操作系统、文件系统权限、Task Scheduler、Polkit、pkexec 和本地 IPC 原语没有被破坏或绕过。

PID、可执行路径、文件所有者和写权限检查只能在这些假设下提供有意义的边界。它们不能证明调用方业务意图正确，不能证明模块内容安全，也不能防御拥有足够本地权限、能够替换受保护文件或改变系统授权配置的攻击者。

## 10. 非目标与已知限制

本实现不是安全 broker、不是通用调用方认证服务、不是沙箱，也不提供通用高安全保证。它不提供模块签名或完整性校验，不对动态模块的行为、依赖或副作用作安全背书，不保证动态模块加载无风险。

本实现也不是常驻特权服务，不提供多请求会话、任务取消、统一的全流程超时、通用任务参数校验、自动回滚或跨平台一致的授权体验。Windows 和 Linux 的安装目录、授权提示、策略管理及失败表现仍以各平台实际配置为准。
